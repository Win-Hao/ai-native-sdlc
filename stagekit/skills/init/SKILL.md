# Set up the toolbox in this repo

The stage commands work without this step — `stagekit/` and the plugin's templates
are the defaults. Running it configures what needs configuring: the gates, the
project's own templates, the pointer in `CLAUDE.md`, and — only if wanted — the
loop driver. Nothing goes live until the user has seen it.

If the argument is `doctor`, skip to **Doctor** below.

## 0. Explore, say what changes, then ask

Explore before speaking: git root, `jq` on PATH, marker files, existing
`CLAUDE.md` / `AGENTS.md`, `.stagekit/`, `stagekit/`, `CONTEXT.md`, `docs/adr/`, and the
language the user writes in. Then tell them in a few lines what setting up means:

- Each change gets `stagekit/<id>/` with `intent.md` → `spec.md` → `plan.md`,
  written by the stage commands when the user runs them.
- Hooks deny or ask on the actions the gate level covers. Nothing else changes.
- By default the agent does not drive the stages; the commands are a toolbox.
- Reversible: delete `.stagekit/` and every hook goes quiet.

Then ask, in one message, leading each question with the recommended answer so
it can be accepted in a word (use `AskUserQuestion` when it is available):

1. **Templates** — English (the plugin's) or 中文 (installed to
   `.stagekit/templates/`, overriding the plugin's). Recommend the language the
   user writes in.

2. **Gate level** — how much the hooks enforce:

   | Level | Gates on | When |
   |---|---|---|
   | `minimal` | irreversible (asks), production_gate | day one — nothing gets in the way except disasters |
   | `standard` | + test_lock, protected_paths | once plan.md and the test-first fix path are in use |
   | `full` | + plan_sync | once plan.md is read before every implementation |

   Recommend `minimal`. `/stagekit:gate` raises it later.

3. **Drive** — `off` (recommended: the agent answers commands, nothing more),
   `suggest` (when new work shows up the agent says once which command would
   capture it, then does what was asked), `auto` (the agent runs the stages and
   stops at each gate — the playbook's end state). If `auto`, also ask which
   pipeline from `${CLAUDE_PLUGIN_ROOT}/pipelines/`: `full` (intent → spec →
   plan → build → verify → review), `lean` (no spec), `regulated` (+ threat-model,
   change-record), `tdd` (build runs test-first, one slice at a time). Otherwise
   record `full` silently;
   `/stagekit:customize` changes it.

4. **What may be written** — a short `## StageKit` block in `CLAUDE.md` (or
   `AGENTS.md` if that is what the repo has) that tells every session where the
   artifacts and commands are; `REVIEW.md` from the template if missing; a
   one-command verification target if the repo lacks one. Recommend the block
   and `REVIEW.md`; the verification target defaults to propose-only.

Do not continue until the user has answered.

## Steps

1. **Confirm the repo.** Root of a git repository, else stop and ask — the
   artifact chain and its audit trail depend on git. `jq` on PATH
   (`command -v jq`), else stop and say so: every hook and the doctor need it,
   and the gates fail closed without it (macOS: `brew install jq`,
   Debian/Ubuntu: `apt install jq`).

2. **Detect the stack and draft a candidate config.** Match the marker files
   against `${CLAUDE_PLUGIN_ROOT}/presets/*.json` (`_detect` field):

   | Marker | Preset |
   |---|---|
   | `package.json` | `node` |
   | `pyproject.toml`, `setup.py`, `requirements.txt` | `python` |
   | `go.mod` | `go` |
   | `Cargo.toml` | `rust` |
   | none / several | `generic`, and say which you saw |

   Copy the preset to a **temporary file** (`/tmp/stagekit-config.json`), not to
   `.stagekit/` — the hooks come alive the moment `.stagekit/config.json` exists. State
   which preset you used.

3. **Correct the candidate against the real code.** A preset is a guess; a glob
   that matches nothing is a gate that protects nothing. Do this even for gates
   that stay off for now, so raising the level later works:
   - `test_globs` — list the repo's real test files (`git ls-files`) and make the
     globs match them.
   - `protected_paths` — the real generated code, migrations, vendored
     directories and frozen packages. Grep for generation headers
     (`Code generated by`, `DO NOT EDIT`, `@generated`).
   - `production_gate.match` — the *actual* deploy commands from the Makefile,
     `package.json` scripts and CI workflows. Patterns that match nothing are
     the most dangerous kind of gate, because they look like protection.
   - `format_command` — the repo's real formatter, or `null`.

   Remove preset entries that do not apply here. An accurate short list beats a
   long inherited one.

4. **Apply the answers** to the candidate:

   ```
   jq '.drive="off"' ...                       # or suggest | auto
   jq --slurpfile p ${CLAUDE_PLUGIN_ROOT}/pipelines/<pipeline>.json '.pipeline=$p[0]' ...
   # gate level
   jq '._gate_level="minimal" | .gates.test_lock.enabled=false | .gates.protected_paths.enabled=false | .gates.plan_sync.enabled=false' ...
   jq '._gate_level="standard" | .gates.plan_sync.enabled=false' ...
   jq '._gate_level="full"' ...
   ```

5. **Preview before it goes live.**
   `${CLAUDE_PLUGIN_ROOT}/scripts/doctor.sh . /tmp/stagekit-config.json` — show the
   user what every glob matches, which deploy patterns were found, which gates
   are on, the drive mode. Fix dead entries, re-run until clean, then **ask to
   confirm**. Only then `mkdir -p .stagekit && mv /tmp/stagekit-config.json
   .stagekit/config.json`, and say that the hooks are now live.

6. **Create the artifact home.** `mkdir -p stagekit`, an empty `.stagekit/current`,
   and `.stagekit/.gitignore` containing `lock-tests` and `.laststate`. For 中文
   templates: `mkdir -p .stagekit/templates && cp ${CLAUDE_PLUGIN_ROOT}/templates/zh/* .stagekit/templates/`.
   Everything else under `.stagekit/` and `stagekit/` gets committed — it *is* the
   audit trail.

7. **The pointer block.** Per answer 4, add this to `CLAUDE.md` (or `AGENTS.md`;
   never create the one when the other exists — if neither exists, ask which),
   replacing an existing `## StageKit` block in place:

   ```markdown
   ## StageKit
   Change artifacts live in `stagekit/<id>/` (intent.md → spec.md → plan.md); the active
   change id is in `.stagekit/current`. Commands: /stagekit:intent /stagekit:spec /stagekit:plan
   /stagekit:build /stagekit:fix /stagekit:verify /stagekit:review /stagekit:done; /stagekit:status shows where a
   change stands. Gates and drive mode: `.stagekit/config.json`.
   ```

   With `drive: auto` add one line: `Never implement without an approved plan.md.`
   If there is no `CLAUDE.md` at all and the user wants one, draft it with
   `/init`, cut it to one page, run every command in it, and leave "Things Claude
   gets wrong" empty — it grows from real mistakes.

8. **`REVIEW.md`** from `.stagekit/templates/REVIEW.md` if the project has one,
   otherwise `${CLAUDE_PLUGIN_ROOT}/templates/REVIEW.md`, with this repo's
   generated paths and whatever CI already enforces filled in — if answer 4
   allowed it; otherwise say `/stagekit:review` will write it on first use.

9. **The feedback loop.** There should be one command that verifies the repo
   and exits non-zero on failure. If there is none, propose a single target
   (`make verify`, an npm script) with its exact content; add it only if
   answer 4 allowed it, and say plainly that `/stagekit:verify` and `/stagekit:build`
   are weaker until it exists.

10. **Run the doctor** (below) on the live config and clear what it reports.

## Doctor

```
${CLAUDE_PLUGIN_ROOT}/scripts/doctor.sh              # live config
${CLAUDE_PLUGIN_ROOT}/scripts/doctor.sh . <file>     # preview a candidate
```

It reports the gate level and drive mode, and per enabled gate how many real
files each glob matches, whether the deploy patterns appear in the build/CI
files, and the state of `CLAUDE.md` and `REVIEW.md`. Then:

- **Every `WARN` about a glob matching nothing** — fix the glob or delete it. A
  config full of dead entries is how people stop trusting the gates.
- **Every `FAIL`** — fix before starting a change.

Report the doctor output, what you changed in response, and — honestly —
anything you could not determine and left as-is.

## Report

What was created, the preset, what you corrected and why, the gate level and
**what it leaves unenforced**, the drive mode, the doctor result. Then how to
start:

- `/stagekit:intent` for the next piece of work; `/stagekit:status` any time.
- Raise the gate level (`/stagekit:gate`) once `plan.md` is actually being read
  before implementation — not before.
- Switch `drive` to `suggest` once the commands feel natural, `auto` when the
  team wants the loop to run itself.
